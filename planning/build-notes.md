## TK-28
- VWM's resolveEntityIdentity is fire-and-forget (void this.resolveEntityIdentity().catch(...)). There is no synchronous signal that the DB write completed. The 4s sleep in task 5 is a heuristic; if the async path races (e.g. NestJS is under load from the drive engine), the Timescale row may not exist yet when pollForNodeCreated runs, causing a false-negative AC-1 failure.
- BindingService.findMatch requires the session-2 observation embedding to be close enough to the session-1 centroid (cosine similarity >= 0.75 matchThreshold). The synthetic mug JPEGs from TK-30 are deterministic (same pixel content both sessions), so the embedding gap should be near-zero — but this assumes the DINOv2 extractor is deterministic (no dropout at inference). If DINOv2 uses a non-deterministic inference path, the two embeddings may diverge and miss the 0.75 threshold, causing a false no-match.
- The test spawns NestJS twice on port 3020. If the first kill does not release the port in time, the second spawn fails with EADDRINUSE. This is the most likely operational failure on Windows (taskkill /T /F is async).
- centroid drift detection (task 5 'ac2:centroid-drift') assumes the session-2 embedding differs slightly from the session-1 stored centroid. If only one sighting occurs in session 1 (sighting_count=1) AND the session-2 observation embedding is bit-identical to the first (same JPEG, deterministic DINOv2), the fold produces `(emb*1 + emb) / 2 = emb` — i.e. no drift. The centroid drift assertion would fail even though the re-bind succeeded. Drift only appears when the second observation's embedding is slightly different from the stored one (which it will be if the crop differs even by 1px, or if DINOv2 has any non-determinism).
- TK-28 depends on TK-30 (fixtures), TK-26 (preflight + stubs), TK-3 (BindingService), and TK-4 (mutable centroids). TK-30 and TK-26 are also todo. If they are built out of order, task 6 (verify) will block at the fixture-exists gate — which is the correct behavior, but means the ticket cannot be closed until TK-26 and TK-30 are done first.
- KG-isolation check (probeNeo4j) runs against the WORLD instance. If the NestJS VWM code has a regression where the VisualObject node is accidentally written to the SELF or OTHER instance, the WORLD query returns found=false and the test fails with a misleading error. The test should also probe that the SELF/OTHER instances have zero VisualObject nodes for the captured nodeId to give a positive isolation signal, not just a null on WORLD.
